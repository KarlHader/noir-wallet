# Incident-derived wallet checks

Use stable IDs to map public failure classes to the audited build. A case can apply without the named product or library if the wallet has an equivalent trust boundary.

- For a comprehensive audit, also look for newer incidents and missing failure classes relevant to the discovered surfaces, chains, shipped dependencies, devices, and distribution channels. In scoped work, look up affected boundaries only. Prefer vendor postmortems, maintainer advisories, and first-party research. Record sources, lookup date, and applicability; distinguish observed incidents, disclosures, and scam patterns.
- Map applicable IDs to the existing coverage ledger. One class can require separate evidence for multiple boundaries. For a nonapplicable row, record why the boundary is absent or unreachable. For unavailable evidence, record the blocked assertion and safe next step. Add genuinely new classes to the current run's ledger before considering changes to this baseline.
- Use read-only tracing, existing tests, or inert local fixtures to check the protective control. Do not replay real attack payloads, run exploit code or incident binaries, develop bypasses, or contact attacker infrastructure. Verify at the actual boundary (review display, signer input, installed package, or synthetic telemetry), not only an intermediate helper.

Vault encryption does not establish that the browser retained no plaintext.                                                                                                              |

State the limits of byte binding if review and signing share a compromise boundary.              |
