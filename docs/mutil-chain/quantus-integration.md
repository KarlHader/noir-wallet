# Quantus Integration Status and dApp Spend Plan

Status: Quantus software-account projection, receive, balance, wallet-native transfer, local transaction monitoring/recovery, and the flagged dApp account/balance provider are implemented in the current source tree. The dApp can relay an externally signed extrinsic through `broadcastExtrinsic` after connection authorization and RPC identity checks; it **cannot** ask the wallet to prepare, sign, and send a transaction. `chain.quantus` is **on** in default builds via `DEFAULT_ENABLED_CHAIN_FEATURE_FLAGS`. Offline checks and the default extension build do not establish a working Quantus-enabled MV3 flow or funded Mainnet/Planck send. This is not a release announcement. The [multichain reference](README.md) owns architectural boundaries and the [release runbook](../release-workflow.md) owns release decisions; use the [transaction lifecycle](architecture/transaction-lifecycle.md) for status and recovery invariants.

## Network and engine boundaries

| Network Mode | Product chain ID  | Native asset     | Bundled RPC                        | Explorer                                                      |
| ------------ | ----------------- | ---------------- | ---------------------------------- | ------------------------------------------------------------- |
| Mainnet      | `quantus:mainnet` | QTC, 12 decimals | `https://rpc1-mainnet.quantus.com` | `https://explorer.quantus.com`                                |
| Testnet      | `quantus:planck`  | PLK, 12 decimals | `https://a1-planck.quantus.cat`    | Planck explorer suitability needs confirmation before release |

Addresses use SS58 prefix 189; the account ID is the Poseidon hash of the ML-DSA public key. Software derivation uses ML-DSA-87 or ML-DSA-65 and the index-0 signing identity. Quantus is an account-based extrinsic chain, not Pearl's UTXO/PSBT/Blockbook model. The packaged WASM accepts `quantus:mainnet`, `quantus:dev`, and `quantus:heisenberg`, but not `quantus:planck`; the host maps Planck to `quantus:dev` **only at the WASM boundary** and registers the Planck genesis hash before signing. The product and RPC continue to use `quantus:planck`. Remove the mapping only after a pinned WASM upgrade supports Planck directly. The WASM exports `prepareQuantusTransfer`, `prepareQuantusCall`, and `confirmQuantusCall`, but no general externally signed extrinsic decoder or Quantus message-signing API. The manifest's `quantus.extrinsic.sign` capability does not imply a released generic dApp signing contract.

Hardware signing, token transfers, quote-deposit/Swap sources, and wormhole addresses/prove/aggregate/exit are not part of this milestone. `deriveQuantusWormhole` remains an unmapped WASM export. No Quantus hardware vendor capability is declared.

The existing relay intentionally follows Pearl's `pushTx` connection-authorized relay model. It must not be reused as the final step of a new dApp spend without the dApp spend's own review, authorization, persistence, and recovery checks. In particular, merely connecting a site does not approve spending wallet funds.

## dApp-initiated native send and signing: implementation plan

**Product requirement:** a connected dApp should be able to ask the wallet to send native QTC/PLK, analogous to Pearl's `sendPearl`, and obtain a wallet-produced signature for a **reviewed native transfer**. These are two distinct operations, both absent today. Scope the first public signing method to the same native transfer contract; do **not** promise generic pallet-call signing, arbitrary extrinsic decoding, message signing, or approval-free signing. Existing `prepareQuantusCall` is an engine primitive, not a safe public call-signing API.

### Public contract and scope

1. Add `sendQuantus(recipient: string, amountRaw: string): Promise<string>` to the injected provider and SDK, with `amountRaw` a canonical positive u128 decimal string in 12-decimal base units, SS58-189 recipient, fixed keep-alive `true`, and the wallet-selected current network/account. The resolved value is the extrinsic hash **only after submission is recorded**; it is not a finality guarantee. Reject unsupported options and extra fields instead of silently accepting them. Reuse `quantus.transfer.v1` and the wallet's provisional fee-ceiling policy; do not accept dApp-supplied nonce, fee, era, signer, RPC, or chain ID. The first implementation should not add a dApp Max shortcut: a balance total is not spendable Max.
2. Implement `signQuantusTransfer(recipient: string, amountRaw: string): Promise<string>` as a required, separate **native-only** operation. Use the same canonical u128/SS58 intent and wallet-owned nonce, era, chain, signer and fee ceiling as `sendQuantus`; return the exact signed `0x` extrinsic **without submitting it**. The dApp may broadcast it later without further approval, including through `broadcastExtrinsic`. The approval must explicitly distinguish “Sign only; the requesting site can submit this transfer” from “Sign and send,” while showing the recipient, amount, signer, network, expiry and maximum fee. Never expose the existing `approve()` result as this API: that method broadcasts and its recovery alarm automatically resubmits signed records. The dedicated signed-only lifecycle below is part of the required implementation, not an optional later enhancement.
3. Keep `broadcastExtrinsic` independent for bytes signed elsewhere. Its caller may not own the active wallet address; it does not substitute for either reviewed wallet operation. Generic `signQuantusCall`/`signTransaction` and `signMessage` require separate on-chain call semantics, trustworthy summaries, authorization and SDK contracts; they are not implied by native-transfer support.

### Implementation sequence

1. **Provider and request validation.** Extend `core/dapp/quantus-provider.ts`, `content-script/inject-provider.ts`, `sdk/src/chains/quantus/types.ts`, SDK detection/example, and the chain-specific allowlists in `lib/runtime-message-security.ts`. Define exact bounded argument shapes and error/return contracts; retain fixed Global Network Mode and `chain.quantus` gating. Reconcile the published [provider guide](../../packages/docs/content/docs/developers/provider-api.mdx) when the public capability actually lands; it currently documents Pearl but not Quantus.
2. **Reviewed dApp send.** Extend `background/quantus-dapp-handler.ts` and `quantus-dapp.ts` to use the existing `BackgroundQuantusTransferController` with the persisted active software ChainAccount, not a duplicate signing or RPC path. Parse the dApp intent; require unlocked origin/chain/account authorization; prepare the transfer through the controller and open a new `quantusTransaction` approval carrying the immutable `quantus.transfer.v1` summary and fingerprint. On rejection or approval-window failure, cancel only the awaiting approval. Immediately before confirmation, recheck origin, permission revision, active account/ChainAccount, network, review fingerprint and expiry. Bind that check to the controller's confirmation boundary (as Pearl does with `approveForDApp`); a pre-approval check alone leaves a race. Never change the approved recipient, amount, nonce, era, or fee ceiling on a late fee/RPC update.
3. **Submission and recovery contract.** Reuse Quantus's signed-fee gate, exact-byte persistence, broadcast and monitor. Return a hash only for recorded broadcast; if signing or submission is uncertain, preserve the same transaction ID and bytes for idempotent recovery, return an explicit pending/unknown error to the dApp, and do not re-sign or report a definitive failure. Check whether the controller needs a dApp-specific `approveForDApp` validation hook and a safe way to recover the result by transaction ID without creating a second transfer. Analytics should be once per reviewed operation, contain no payload or address, and not double-count popup recovery.
4. **Required signed-only lifecycle.** Add a distinct `sign-only` intent and a versioned, strictly parsed signed-only record in `infrastructure/chains/quantus/quantus-pending-transfer-store.ts`, with origin, account scope/ChainAccount, network, approved intent/fingerprint, one-time command ID, nonce, era, fee ceiling and status. Do not reuse the existing `signed` pending-transfer phase: `resumePendingBroadcasts()` iterates **all** such records and submits their bytes. Introduce separate `awaiting-approval → signing-in-progress → signed-for-delivery → delivered/expired` transitions (or a comparably explicit state machine) under an account-scoped serialization/claim lock shared with wallet sends. Persist the `signing-in-progress` claim **before** Worker `confirm`; a lost confirm response must remain indeterminate, never prepare/sign again or release a nonce on a timer alone. After confirm, validate signer, account, nonce, era, encoded native call, reviewed summary and local extrinsic hash against the **exact** returned bytes; the current signed-fee gate does not decode the call or independently prove that binding. Provide a bounded native-extrinsic verifier or a separately pinned WASM verification API before claiming this check, then run the signed-fee/balance gate and persist the signed bytes and record **before** returning them. If any validation fails, never return the bytes. Neither the transaction monitor nor startup alarm may broadcast a signed-only record, and merely returning bytes must not mark a graph `broadcast` or `final`.
5. **Nonce, expiry and external submission.** While a signed-only request can still be submitted, prevent wallet sends or further sign-only approvals from unknowingly reusing its `(chain, signer, nonce)`; a current RPC nonce alone cannot prove that unbroadcast bytes are harmless. Bound signing to a mortal era (no immortal sign-only extrinsic), reject an expired era before delivery, and settle reservations only after conclusive expiry/non-submission or chain evidence that the nonce has been consumed; define how a concurrently submitted external extrinsic or changed RPC nonce is reconciled, failing closed when ambiguous. If users need overlapping sends, first implement a pending-aware nonce allocator and prove it against both wallet and dApp signing paths. Do not allow account/network switching, a dApp disconnect, or wallet reset to erase an already released signature's risk while it remains valid.
6. **Exactly-once delivery and recovery.** Bind a bounded idempotency identifier to origin, authorized account, network, immutable intent/fingerprint and signing operation; concurrent/replayed requests for the same identifier must return the same result or an explicit pending outcome, never create another signature. A later retry is allowed to retrieve persisted bytes **only** for the same authorized origin and unchanged account/network while they remain valid; never expose bytes across origins. If a response is lost after signing, the Background must distinguish `signed-for-delivery` from `delivered` without pretending to know whether the dApp received the bytes; recovery may return the same bytes after reauthorization but must never automatically broadcast or sign anew. On service-worker restart, reconcile the persisted claim and session record; if browser restart loses `chrome.storage.session` bytes, keep a non-replayable indeterminate marker and return an explicit unrecoverable outcome rather than silently re-signing. Specify and test how records are securely cleared on expiration, wallet removal and explicit account deletion, without making premature cleanup a nonce-reuse signal.
7. **Signed-only approval, provider and tests.** Add a distinct `quantusSignTransfer` action to the Background approval/cancellation list, popup parser and `ApprovalPage.tsx`; accept only a validated immutable `quantus.transfer.v1` review and show origin plus the fact that no broadcast occurs. Recheck origin permission revision, wallet/account/ChainAccount, network, fingerprint and expiry **inside** the signing claim/confirm boundary; cancellation and rejection must cancel only requests still awaiting approval, not erase an in-flight or already released signature. Add SDK/provider and runtime-message limits for the signed hex result as well as input. Exercise approval/rejection, account or authorization changes at each await, same-origin retry and cross-origin denial, concurrent requests, Worker crash before/after confirm, lost response, session/browser restart, era expiry, consumed/ambiguous nonce, fee failure, no automatic submission, and optional later `broadcastExtrinsic` with the same bytes. Use a real flag-enabled MV3 extension for delivery and restart behavior; funded broadcast/finality checks require explicit authorization.

### Release and acceptance boundary

`chain.quantus` stays off by default until a real isolated MV3 extension proves software unlock/receive/balance, reviewed wallet send, one-time submission, uncertain-state recovery and definitive activity status on the intended network(s). dApp send additionally requires evidence that rejection never signs or submits, approval cannot outlive permission/account/network changes, and responses do not claim finality. **`signQuantusTransfer` is required for the dApp milestone**, with a separate acceptance gate: only a reviewed native transfer is signed; bytes are returned solely to the authorized site, exactly once per intent (or the same persisted bytes on retry); no wallet broadcast occurs; pending signatures cannot reuse the nonce unsafely; and lost-response/restart states never trigger a second signature. If these invariants are not yet demonstrable, keep that method unavailable and report the blocker rather than shipping a weaker fallback. Do not treat passing offline tests, packaged WASM exports, or the externally signed relay as proof of these gates.

## Verification snapshot and remaining work

- The packaged Multichain WASM manifest and loader/binary integrity gate, Quantus derive and prepare/confirm contract tests, offline address/RPC/portfolio/summary tests, and extension type-check/default build have passed locally during this worktree's development. These are **not** Quantus-enabled MV3 or funded acceptance.
- Wallet-native send, monitor, recovery and popup paths exist in source; the previous “transfer stub,” “no send form,” and “broadcast disabled” descriptions were obsolete. `broadcastExtrinsic` is now a connection-authorized external relay, not a reviewed wallet-native transfer.
- No `quantus` Playwright project is registered in `packages/extension/scripts/run-tests.mjs`, and no Quantus-specific real-extension spec or funded transaction result has been verified here. External transaction history, Planck explorer confirmation, secure browser-restart signed-byte recovery and the new dApp send/sign interfaces remain open or separately scoped as described above.
